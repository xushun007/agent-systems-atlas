Agent Inheritance Hierarchy

  • BaseAgent ABC
    Abstract base class. Defines run_async, run_in_new_context, before/after callbacks, state management via BaseAgentState.
    • LlmAgent (Agent) DEFAULT
      Most common agent type. model + instruction + tools + planner. Exported as `Agent` from google.adk.
      • model: str PROP
      • instruction: str PROP
      • tools: list[BaseTool] PROP
      • planner: BasePlanner PROP
      • code_executor: BaseCodeExecutor PROP
      • sub_agents: list[BaseAgent] PROP
    • LoopAgent
      Runs child agents in a loop. Terminates when ExitLoopTool is called or max_iterations reached.
      • child_agent: BaseAgent
      • max_iterations: int
    • SequentialAgent
      Executes child agents in defined order. Passes accumulated context between them.
      • agents: list[BaseAgent] ORDERED
    • ParallelAgent
      Runs child agents concurrently via asyncio.gather. Aggregates results.
      • agents: list[BaseAgent] PARALLEL
    • LangGraphAgent
      Wraps a LangGraph graph/StateGraph as an ADK agent for interoperability.
    • RemoteA2aAgent
      Remote agent communication via A2A (Agent-to-Agent) protocol.

Workflow Node Hierarchy

  • BaseNode ABC
    Contract for all workflow nodes. Supports output streaming via AsyncGenerator[Event] and human-in-the-loop steps.
    • Workflow ENGINE
      Graph orchestration — START → edges → nodes → END. Implements _run_impl() as the orchestration loop.
      • Graph — directed graph with nodes and edges
      • Edge / EdgeItem — conditional and unconditional transitions
      • Trigger — condition-based edge activation
      • DynamicNodeScheduler — runtime node scheduling
      • ParallelWorker — concurrent branch execution
      • ReplaySequenceBarrier — replay/rehydration support
    • FunctionNode
      Executes a synchronous or async Python function. Returns result as Event.
    • ToolNode
      Executes tool calls within a workflow. Handles tool confirmation and results.
    • LlmAgentWrapper
      Wraps an LlmAgent as a BaseNode so it can be included in a workflow graph.
    • JoinNode
      Convergence point — waits for all incoming branches to reach terminal state before proceeding.

Why Runner / NodeRunner Separation?

If Runner and NodeRunner were merged, nested workflows would cause deadlocks — the inner workflow's NodeRunner would block the outer Runner's event consumption. Three-layer separation prevents this:

Runner (lifecycle) → NodeRunner (scheduling) → Workflow (graph traversal)

Event Lifecycle — One Invocation

1

Runner.run_async()

Entry point. Parameters: app_name, user_id, session_id, new_message

2

Create InvocationContext

Per-invocation singleton. Wires up: session_service, memory_service, artifact_service, credential_service, plugin_manager, _event_queue (asyncio.Queue)

3

Load Session History

Fetch prior events from session store. Build context window from recent events. Apply app:, user: state merges.

4

Create RequestInput Event

Wrap user message as Event with EventActions.REQUEST_INPUT. Append to session via append_event().

5

Request Pipeline Processing

Processors run in order: basic → instructions → contents → code_execution.request_processor

6

LLM Call (BaseLlm.run_async)

Build LlmRequest, call model, receive streaming LlmResponse with Content chunks. Plugin around_llm_call() wraps this.

7

Response Pipeline Processing

nl_planning → code_execution.response_processor (extract code blocks, execute, wrap results)

8

Tool Call Loop (if applicable)

LLM returns function calls → ToolNode executes → FunctionResponse Event → back to LLM. Repeat until no more tool calls.

9

Events Stream via EventQueue

Events written to ic._event_queue (asyncio.Queue). Runner consumes them. done_sentinel marks completion.

10

Return AsyncGenerator[Event]

Caller receives streaming events. Session state persisted. Plugin after_agent() hooks fire.

Key Design Decisions

Runner / NodeRunner Separation

Q: Why not merge Runner and NodeRunner?
A: Nested workflows would deadlock — inner NodeRunner blocks outer Runner's event consumption. Three layers prevent this.

Event as Single Data Flow

Q: Why everything through Event?
A: All interactions (messages, tool calls, responses) flow through Event. Enables persistence, replay, evaluation, and streaming.

Context 1:1 Node Mapping

Q: Why each node gets its own Context?
A: Isolates node state, output, route decisions, and interrupt IDs. Prevents cross-node state pollution.

InvocationContext Singleton

Q: Why one InvocationContext per call?
A: Shares services and event queue across all nodes in a single invocation. Avoids recreating connections and state.

State Prefix Routing

Q: Why app:/user:/temp: prefixes?
A: Different scopes have different lifecycles. App = global, User = cross-session, Temp = invocation-only, Session = isolated.

Plugin Hook System

Q: Why before/after/around hooks?
A: Cross-cutting concerns (tracing, logging, filtering, retry) are decoupled from core logic. Composable and optional.

Dual Execution Paths

Q: Why maintain two execution paths?
A: New node runtime (ADK 2.0) supports Workflow and BaseNode. Old plugin path provides backward compatibility during migration.
