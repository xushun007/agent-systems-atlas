# Session、Turn 与 Step：Coding Agent 的状态所有权与执行边界

Coding Agent 的一次任务执行通常包含多次模型请求和工具调用。执行期间，用户仍然可以追加要求、响应审批或修改配置；模型请求、工具进程和会话存储则按照各自的生命周期推进。Runtime 必须确定这些操作的执行归属、状态更新顺序及生效边界。

Session、Turn 与 Step 为描述这些责任提供了不同粒度：Session 表达会话的长期身份，Turn 表达一轮工作的执行范围，Step 表达其中一次具体推进。但仅有层次划分并不足以建立一致性保证。还需要明确每类状态由谁维护、何时被读取，以及如何关联到实际发生的操作。

本文从持续交互中的输入可见性问题出发，建立状态所有权的分析框架，并通过 Codex、Kimi Code 和 mini-SWE-agent 的固定版本实现说明这些边界。本文中的统一术语用于跨项目分析；具体项目采用的对象名称和生命周期可能不同。

## 1. 问题定义：输入接收与执行生效之间的关系

考虑一个常规交互过程：Agent 正在修改接口，用户随后补充“保持现有接口兼容，不修改调用方”。若后续修改仍然涉及调用方，需要首先区分两类原因。

第一类是输入尚未进入产生该修改的模型请求，例如它仍在等待队列中，或被安排到下一轮执行。第二类是输入已经进入请求，但模型生成的动作没有遵循要求。前者涉及 Runtime 的输入接纳与可见性；后者涉及模型行为。最终代码和聊天记录通常不足以区分二者。

对一条追加输入，应分别观察以下状态：

| 状态 | 所表达的事实 | 需要进一步确认的事项 |
| --- | --- | --- |
| 入口接收 | 某个客户端或服务端入口已收到操作 | 核心 Runtime 是否接纳该操作 |
| 执行归属确定 | 输入已绑定到当前或后续执行 | 是否已加入相应的模型上下文 |
| 请求包含输入 | 某次模型请求携带该输入 | 模型输出是否遵循要求 |
| 动作执行完成 | 工具已产生执行结果或外部副作用 | 结果是否被正确关联、记录与展示 |

这些状态不必对应四个独立组件，但具有不同的语义。客户端回显不能代替服务端接纳，请求发送不能代替工具执行，工具完成也不能单独证明结果已持久化。

本文将一致性问题限定为：**输入、配置、模型请求和工具结果之间，是否存在明确且可核验的归属与生效关系。** 这一分析不直接承诺事务原子性、线性一致性或恰好一次执行。此类保证需要针对具体操作及存储协议单独证明。

问题的普遍性来自执行中交互这一能力。只要 Runtime 允许新操作与已有执行在时间上重叠，就需要定义它们如何协调。不同产品中的实际发生频率不属于本文的证据范围。

## 2. Session、Turn 与 Step 的语义边界

### 2.1 Session：会话身份与跨轮次状态

Session 用于关联属于同一会话的交互、配置和历史。它提供跨轮次的连续性，但不要求这些数据由同一个对象保存。

会话身份、持久化记录和活跃执行实例应分别考察。恢复会话可以创建新的执行实例；执行实例结束后，历史记录仍可保留。因此，会话存在与会话正在执行是两个不同的判断。跨进程恢复能力也需要存储和重建机制支持，不能仅由 Session 这一名称推导。

在比较不同实现时，应明确 Session 负责哪些状态、委托哪些服务，以及哪些资源的生命周期独立于它。

### 2.2 Turn：一轮工作的执行范围

本文用 Turn 表示一轮被 Runtime 接纳、具有开始和终态的工作。它可能包含多次模型请求和工具调用，也可能接收执行期间追加的输入。

用户消息与 Turn 不必一一对应。追加消息可以进入活跃 Turn，也可以形成后续 Turn；系统触发的继续执行也未必来自新的用户消息。具体映射取决于输入接纳规则。

Codex 的 `steer_input()` 提供了一个明确的实现例子：它检查活跃任务是否存在、是否支持 steer，并在调用方提供预期 Turn ID 时检查身份是否匹配。接纳成功后，输入写入该 Turn 的待处理队列，并返回 Turn ID。活跃任务检查与队列更新处于同一个受锁保护的操作范围。[^codex-steer]

这段逻辑建立了输入与目标执行之间的关联。预期 Turn ID 的检查用于拒绝目标已经变化的操作；它所证明的是接纳时的执行归属，而非输入已经进入模型请求。

### 2.3 Step：一次具体推进的执行条件

Step 用于细分一轮工作，使某次推进能够关联到当时的输入、配置和结果。但 Step 在不同项目中具有不同粒度。

Codex 的 `StepContext` 属于一次模型采样请求，关联其 Turn，并保存捕获的设置版本、执行环境、MCP 绑定、工具路由和 `AGENTS.md` 等信息。工具路由字段明确用于同一次请求的工具暴露与执行。[^codex-step]

mini-SWE-agent 的默认 `step()` 则组合模型查询、动作执行和观察结果追加。`run()` 反复调用这个单位，处理退出及轨迹保存。这里的 Step 覆盖模型与工具的一轮交互。[^mini]

因此，跨项目比较必须先核对实际执行边界，才能比较取消、重试或恢复的保证。名称相同并不意味着语义等价。

### 2.4 Attempt：逻辑推进与实际尝试

当一次请求发生重试时，同一个逻辑目标可能对应多次实际尝试。本文以 Attempt 区分这一层关系，不要求项目具有同名类型。

这一概念用于避免把“继续完成同一项工作”与“重复发起了一次执行”混为一谈。对于只涉及模型请求的重试，主要问题是请求和结果归属；对于已经产生外部副作用的工具重试，还需要判断动作是否重复。后者将在恢复专题中讨论。

## 3. 状态所有权的四个维度

状态所有权描述维护状态及其约束的责任。它不等同于对象创建者，也不只取决于数据存放的位置。

例如，界面可以保存一条输入的展示副本，但输入是否进入活跃执行，由接纳逻辑决定；历史服务可以保存审批记录，但执行器是否继续，需要审批等待状态与该记录正确关联。分析时应区分以下四个维度：

| 维度 | 定义 | 需要核对的机制 |
| --- | --- | --- |
| 身份归属 | 状态关联的会话、执行或工具调用 | 标识及关联关系是否稳定 |
| 写入责任 | 状态更新的授权组件及协调方式 | 单一写入者、锁、队列或冲突处理 |
| 可见性边界 | 状态更新被后续操作读取的时点 | 接纳点、上下文构建点、执行前检查点 |
| 生命周期与保存 | 状态何时失效，哪些内容需要跨进程保留 | 清理、持久化、重建及恢复规则 |

这四个维度可能由不同组件承担。设计上需要明确的是责任之间的连接，而不是要求全部状态集中到一个管理对象。

### 3.1 配置归属与生效范围

配置属于 Session，并不意味着它必须在整个 Session 内保持不变；配置发生变化，也不意味着正在执行的请求会立即使用新值。

例如，默认模型可以作为会话配置保存，每次构造请求时读取一个确定的版本。此时，配置的生命周期长于请求，具体请求仍有自己的执行条件。审批规则、工具集合和工作目录也需要分别定义读取时点，不能假定它们与模型设置采用相同的更新规则。

Codex 将请求级信息放入 `StepContext`，同时在 `TurnState` 中保存待处理输入、审批等待者和最近使用的 Step 上下文，体现了请求条件与活跃执行状态的区分。[^codex-step] 这种结构有助于追踪请求使用的条件，但仅凭结构定义，尚不能证明跨组件更新具有原子性。

### 3.2 可变性需要落实到具体状态

Session、Turn、Step 都不能整体归类为“可变”或“不可变”。同一个执行范围内，可以同时存在固定身份、已捕获的请求参数、持续更新的流式输出以及可被取消的等待状态。

判断可变性时，应说明具体字段或记录在什么阶段允许变化。例如，请求准备期间可以调整输入；请求发出后，后续更新是否能够影响它，取决于传输协议和 Runtime 的处理机制。普通请求不会因为本地消息列表改变就自动获得新输入。

历史记录同样需要具体分析。追加式日志、可编辑消息列表和压缩后的上下文具有不同语义。“记录不可变”不能单独证明记录完整，也不能证明该记录已经可靠落盘。

## 4. Runtime 中需要区分的状态

为了追踪更新和可见性，可以按用途将状态划分为五类。这是分析框架，不要求实现中存在五个独立模块。

| 状态类别 | 典型内容 | 主要一致性问题 |
| --- | --- | --- |
| 历史记录 | 输入、模型输出、工具结果、结束原因 | 记录对应什么事实，是否完整保存 |
| 可变配置 | 模型选择、权限规则、可信目录 | 更新由哪些执行读取，从何时生效 |
| 活跃执行状态 | 待处理输入、审批等待者、取消信号 | 谁负责推进、终止和清理 |
| 派生视图 | 模型上下文、压缩摘要、界面展示 | 来源是什么，何时更新，是否可重建 |
| 外部状态 | 文件、Git 工作区、工具进程 | 如何检测其他执行者造成的变化 |

这种划分有两个直接用途。

首先，它区分历史保存与请求构造。消息被写入会话历史，可以满足追溯或恢复需求，但不一定意味着某次已经发出的请求包含该消息。请求上下文需要结合选取范围、处理顺序和压缩等规则单独确定。

其次，它区分 Runtime 控制的状态与外部资源。模型读取文件后，用户或其他进程仍可能修改文件。捕获模型参数和工具绑定不会冻结文件系统；工作区的一致性还需要内容匹配、版本检查或隔离机制支持。

在范围较小的实现中，多项责任可以由同一对象承担。mini-SWE-agent 的默认 Agent 集中持有消息、模型、环境和调用计数，并通过同步控制流组织查询与执行。[^mini] 这种设计降低了内部协调成本。是否需要进一步拆分，取决于持续输入、并发任务和持久化恢复等需求，不能仅按组件数量评价架构。

## 5. 实现证据：接纳、物化与历史记录是不同边界

### 5.1 Kimi Code：请求出队与上下文物化分离

Kimi Code `v0.40.0` 的 v2 实现区分请求的 `pending`、`materialized` 和 `aborted` 状态。`StepRequestQueue` 负责排队、批次选取和过滤已撤回请求；`AgentLoopService` 则负责将请求解析为消息并追加到上下文，再标记请求已物化。[^kimi-request] [^kimi-loop]

这里的“物化”特指待处理请求被转换为上下文输入，不等同于模型请求已经发送。

本专题直接调用上游原始请求类与队列类进行了局部实验，得到以下观察：

| 操作 | 观察结果 |
| --- | --- |
| 请求入队 | 请求处于 `pending`，队列存在待处理项 |
| 请求被取出 | 队列可以为空，请求仍处于 `pending` |
| 显式标记物化 | 请求变为 `materialized`，请求级 `abort()` 返回 `false` |
| 撤回等待中的请求 | 请求变为 `aborted`，队列不再返回它 |
| 合并普通请求与可合并请求 | 一个批次包含两个请求，取出时两者仍处于 `pending` |

实验支持两个有限结论：队列位置与请求处理状态相互独立；输入数量与执行批次数量不必相等。实验中的物化标记由脚本显式调用，没有执行完整 Loop、上下文追加或模型请求。

实际 Loop 中“先追加上下文，再标记物化”的顺序来自源码阅读。上游还提供了排队 Turn 在启动和应用初始输入之前被撤回的测试，以及取消一个 Step 后继续同一 Turn 的测试。[^kimi-tests] 这些测试反映了实现预期，但本次完整 Loop 测试未能通过依赖加载阶段，因此不计入已运行验证。

请求级 `abort()` 与执行级取消也应分开理解。已物化请求不能再按等待中的输入撤回，并不意味着其关联的 Step 或 Turn 无法取消；二者作用于不同状态。

### 5.2 Codex：历史记录不能单独证明请求可见性

Codex 的一项测试检查任务结束时如何处理尚未消费的追加输入：先创建活跃任务并追加输入，再触发任务结束，随后断言剩余输入进入会话历史，并产生相应的消息生命周期事件。[^codex-history]

这项测试表明，保存已接纳输入与将输入用于模型请求具有不同的处理边界。即使后续能够从会话历史中找到一条消息，也不能仅据此断言先前的请求包含它。

验证请求可见性，需要直接检查目标请求，或依据完整的版本与顺序信息重建其输入。对于没有保存完整请求的实现，历史记录能支持的结论应相应收窄。上述测试检查的是会话历史，也不能单独证明磁盘持久化已完成。

### 5.3 对状态所有权的解释

Kimi 的请求队列与 Codex 的历史处理分别说明了两个问题：请求交接之后仍有独立的应用阶段；输入保存之后仍需单独判断其请求可见性。

因此，状态所有权模型需要记录各阶段的交接条件。至少应明确谁接纳输入、谁决定执行归属、谁将其纳入上下文，以及谁保存处理结果。这些责任可以集中实现，也可以由多个组件协作，但仅有 Session、Turn 和 Step 的标识不足以证明交接正确。

## 6. 一致性分析与验证方法

在上述框架下，可以将验证分为三个问题。

**归属是否明确。** 对追加输入、审批回复或取消请求，应确定它针对哪个执行，以及目标已变化时如何处理。Codex 的预期 Turn ID 检查是这一问题的具体实现证据。

**可见性是否可追踪。** 对一项配置或输入更新，应能确定哪些请求或工具操作使用了它。队列入队、上下文应用和请求发送是不同观察点，需要分别记录。

**生命周期是否闭合。** 对已经接纳的操作，应能判断其仍在等待、已经执行、被拒绝或被取消。尤其需要检查执行终止时，剩余输入和等待者由谁处理。这是一项验证要求，不表示本文已经证明所有项目满足该性质。

对于“执行中追加要求”的完整实验，可以先让一个受控工具阻塞，在确认前一请求已发出后提交新输入，再释放工具，捕获后续请求及调用结果。屏障用于固定操作顺序，确定性模型响应用于减少生成差异。真实模型实验可随后验证产品入口和实际传输路径。

实验应同时保留输入身份、执行身份、目标请求内容和工具调用关联。请求未包含要求与模型未遵循要求，需要根据这些证据分别判断。界面截图和最终回复只能提供辅助信息。

本文已完成的实测范围限于 Kimi 的请求与队列类。[第二篇](02-input-admission.md)进一步运行了 Pi 底层 Agent 的输入可见性实验，观察点为模型适配函数入口；真实提供商链路的端到端验证尚未完成。

## 7. 本文结论与适用范围

Session、Turn 与 Step 提供了会话身份、工作范围和执行粒度三个层次。状态所有权进一步明确每类状态的写入责任、可见性边界及生命周期。二者结合，才能解释输入和配置如何影响执行。

现有实现证据支持以下判断：用户消息与 Turn 没有必然的一一对应关系；请求出队与输入应用可以分离；历史记录不能单独证明请求可见性；请求级执行条件与可变执行状态可以共存。这些判断用于识别需要验证的边界，不构成对所有 Coding Agent 的统一协议要求。

执行快照与外部工作区、前台 Turn 与后台任务也需要分别考察。本文不从 Session / Turn / Step 的主执行关系推导完整的资源所有权树，不将局部状态机正确性扩大为跨进程或外部副作用的一致性保证。

后续文章将沿着输入接纳过程，进一步研究排队、steer、审批和配置更新的具体生效规则。
